## 0. 30초 요약

**오프라인 온보딩 AI 코드 어시스턴트**의 검색 계층입니다.
신입 개발자가 낯선 코드베이스에 대해 질문하면, 레포에서 근거를 찾아
**출처와 함께** 답하게 하는 것이 목표입니다.

```
[VSCode Extension]  질문
        ↓
[백엔드]            오케스트레이션 · LLM 호출 · 스트리밍
        ↓
[rag_lab]  ← 이 레포. 검색 + 프롬프트 조립
        ↓
[Ollama]            임베딩(bge-m3) + 생성(qwen2.5-coder:7b)
```

**현재 동작합니다.** 인덱싱·검색·프롬프트 조립이 실제로 돌고, 백엔드 연동 중입니다.

## 2. 설계 결정과 근거

⚠ **근거를 모르고 되돌리면 안 되는 것들입니다.**

### 임베딩 · 검색

| 결정 | 근거 |
|---|---|
| **BGE-M3 고정** | 다국어 — 한국어 질문 ↔ 영어 코드가 통해야 함. 실측 Hit@3 90% |
| **cosine 고정** | 임계값 0.54 의 전제 |
| **저장소는 자유** | 점수를 만드는 건 임베딩과 거리함수. 저장 위치는 무관 |
| **Chroma 선택** | 벡터 + **원문 + 메타데이터**를 한 곳에 → 별도 DB 불필요 |
| **fallback 없음** | 가짜 임베딩이 조용히 인덱스를 오염시킨 사례가 있었음 |

### 인덱싱

| 결정 | 근거 |
|---|---|
| **git commit + fingerprint** | commit 만 비교하면, 청킹 파라미터를 바꿔도 "최신"으로 오판 |
| **`job_id` 미사용** | 동시 인덱싱이 없음 → `project_id` 로 충분 |
| **threading** | Redis 6개 기능 중 필요한 건 비동기 실행·진행률 2개뿐 |
| `STALE_AFTER=120` | 프로세스 중단 시 `running` 고착 → heartbeat 2분으로 판정 |

### 프롬프트 · 출처

| 결정 | 근거 |
|---|---|
| **프롬프트 조립을 rag_lab 이 함** | fine-tuning 학습 데이터와 **같은 코드**를 써야 형식이 안 갈라짐 |
| **LLM 호출은 백엔드가 함** | 스트리밍 중계 단계를 줄이기 위해 |
| **출처 2층 구조** | 검색 단위는 파일이 아니라 청크. 같은 파일이 3번 나오는 게 정상 |
| **`n` 번호 유지** | 인용된 것만 추려도 재번호 금지 — 답변의 `[3]` 이 깨짐 |
| **history 0턴 권고** | 길면 근거를 밀어냄. 실사용에서 품질 저하 관찰됨 |

### 성능 실측 (서빙 환경 기준)

```
prefill   0.34 ms/token + 209ms 고정비   → 근거 2,400토큰에 1.0초
decode    약 53 tok/s                    → 300토큰 답변에 5.9초
콜드스타트 7.3초                          → 첫 요청 타임아웃 주의
num_ctx   8,192
```

⚠ **decode 가 병목입니다.** 답변 길이를 150~250 토큰으로 통제하지 않으면
응답이 길어집니다. 스트리밍이 필수인 이유이기도 합니다.

## 3. 외부 의존

| 대상 | 주소 | 비고 |
|---|---|---|
| Ollama | `VSS_OLLAMA_URL` (기본 `127.0.0.1:11500`) | ⚠ SSH 터널 경유 |
| 임베딩 모델 | `bge-m3:latest` | 서버에 pull 되어 있어야 함 |
| 생성 모델 | `qwen2.5-coder:7b` (Q4_K_M) | rag_lab 은 직접 호출 안 함 |

### ⚠ 터널 의존이 현재 가장 취약한 지점

임베딩이 원격 호출이라, 터널이 끊기면 인덱싱·검색이 전부 멈춥니다(503).

**로컬 임베딩 전환이 검토 중**입니다.
`sentence-transformers` 로 `BAAI/bge-m3` 를 직접 돌리면 벡터가 동일하므로
(cosine 1.0000 확인됨) 인덱스 호환성 문제 없이 전환 가능합니다.

전환 시 `embedder.py` 만 교체하면 되고, 나머지는 손댈 필요 없습니다.

## 4. 백엔드 연동 계약

상세는 `API.md`. 요약하면:

```
① POST /prompt    {query, project_id}
   → {has_evidence, messages, sources, references, reference_files, stage, timing}

② 백엔드가 Ollama /api/chat 에 messages 를 그대로 전달 (스트리밍)

③ POST /finalize  {answer, sources}
   → {answer, references, reference_files, cited, no_evidence}
```

### 🔴 반드시 지켜야 할 것

| 항목 | |
|---|---|
| `has_evidence: false` | **LLM 을 호출하지 말 것.** 근거 없이 물으면 지어냄 |
| `sources` 배열 순서 | 변경·정렬·필터 금지. `[N]` 대응이 깨짐 |
| `references[].n` | 재번호 금지 |
| 타임아웃 | `/prompt` 60초, Ollama 120초 이상 (콜드스타트 7.3초) |

## 5. 알려진 미해결 — 우선순위 순

### 🔴 1. 평가셋이 없습니다

**지금 가장 큰 공백입니다.**

```
검색은 되는데 "좋은지"를 판정할 방법이 없음
   ↓
청킹 파라미터를 바꿔도 개선인지 악화인지 모름
   ↓
chunk_size=1200, top_k=4 는 근거 없이 정해진 값
```

필요한 것: 질문 15~20개 + **정답 근거(파일·라인)**

이게 나오면 동시에 풀립니다.
- 청킹 실험 (Hit@3 비교)
- 임계값 0.54 검증
- 문서 검색 미검증 문제
- fine-tuning 학습 데이터 시드

### 🔴 2. `/prompt` 지연 미측정

```
TTFT = /prompt 시간 + Ollama prefill(1.0초)
```

`/prompt` 가 2초면 스트리밍을 붙여도 첫 글자까지 3초입니다.

```bash
python bench_ttft.py --project <이름> --repeat 5
```

`embed_ms` 가 1초 이상이면 터널이 병목 → 로컬 임베딩 전환 근거.

### 🟠 3. 인덱싱 55분

실험 반복도 데모도 불가능한 시간입니다.

| 수단 | 효과 |
|---|---|
| 대상 레포 축소 | 🟢 가장 확실 |
| 로컬 임베딩 | 🟢 터널 왕복 제거 |
| 배치 확대 (16→64) | 🟡 병목이 터널일 때만 |

### 🟠 4. `project_root` 경로 문제

```
Extension:  개발자 PC 의 workspace 경로
rag_lab:    다른 머신에서 실행 중
            → 그 경로가 존재하지 않음
```

**현재 구조로는 "임의 프로젝트 인덱싱"이 성립하지 않습니다.**
아키텍처 결정이 필요합니다(개발자 PC 마다 rag_lab 배포 / 파일 업로드 / 데모 한정 등).

### 🟡 5. 상태 영속성

`data/state.json` 은 1단계 구현입니다. 프로세스가 죽으면 진행 중이던 작업 상태가
소실됩니다(인덱스 자체는 남음). SQLite 로 옮기는 것이 2단계 계획입니다.

## 6. 파라미터의 근거 상태

⚠ **정직하게 — 상당수가 임시값입니다.**

| 값 | 현재 | 근거 |
|---|---|---|
| `embed_model` | bge-m3 | 🟢 **실측** |
| `score_threshold` | 0.54 | 🟢 **실측** (0.5306 ~ 0.5531 사이) |
| `chunk_size` | 1200 | 🔴 **임의값** |
| `chunk_overlap` | 150 | 🔴 **임의값** |
| `top_k` | 4 | 🔴 **임의값** |
| `min_chunk_chars` | 80 | 🔴 임의값 |
| 청킹 전략 (줄 윈도우) | — | 🔴 **검증 안 됨** |

### 청크 크기에 대한 메모

**BGE-M3 는 8192 토큰까지 받습니다.** 1200자는 한참 여유입니다.
즉 **모델 제약 때문에 자르는 게 아니라, 검색이 잘 되게 하려고 자릅니다.**

```
너무 크면  →  한 조각에 여러 주제 → 점수가 흐려짐
너무 작으면 →  함수가 중간에 잘림 → LLM 이 맥락 없이 설명
```

**최적값은 평가셋 없이 정할 수 없습니다.**

### 청킹 전략 대안

현재는 줄 단위 윈도우입니다. 코드에는 AST 기반(함수·클래스 단위)이 더 나을 수
있지만 검증되지 않았습니다. "이 함수 뭐 하는 코드?" 시나리오에서 함수가 반토막
나면 답변 품질이 떨어집니다.

## 8. 용어

| 용어 | 뜻 |
|---|---|
| **청킹** | 파일을 조각으로 자르는 것 |
| **임베딩** | 텍스트를 1024개 숫자(벡터)로 바꾸는 것. **검색용이지 LLM 입력이 아님** |
| **cosine similarity** | 두 벡터가 얼마나 비슷한가. 1.0=같음, 0=무관 |
| **임계값** | 이 점수 미만이면 "근거 없음"으로 판정하는 선 |
| **top_k** | 검색 결과를 몇 개 가져올지. **청크 개수이지 파일 개수가 아님** |
| **fingerprint** | 인덱스를 만든 파라미터 조합. 바뀌면 재인덱싱 필요 |
| `[N]` | 답변 안의 인용 마커. `references` 의 `n` 과 대응 |

### 🔑 자주 오해되는 것

> **LLM 은 벡터를 보지 않습니다. 원문을 봅니다.**

임베딩은 "어느 조각을 고를지" 정하는 데만 쓰이고,
고른 뒤에는 **원문 텍스트를 그대로** 프롬프트에 넣습니다.

## 9. 이 레포 밖의 맥락

프로젝트 전체 상태(일정·마일스톤·팀 분담·fine-tuning 계획)는 별도 문서에 있습니다.
이 레포만으로 작업할 때는 위 내용으로 충분하지만, 아래가 필요하면 요청하세요.

- `PROJECT_STATE` — 결정 레지스트리 · 일정 · 리스크
- `PROMPT_DATA_FORMAT_SPEC` — 학습 데이터 형식 (프롬프트 형식과 연동)
- `RAG_LAB_INTEGRATION` — 백엔드 연동 가이드

⚠ **`PROJECT_STATE` 는 2026-08-03 기준이라 일부 항목이 이 문서보다 오래됐습니다.**
충돌하면 이 문서가 최신입니다.
