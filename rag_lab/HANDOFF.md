## 2. 🔴 2026-08-06 관측 — 가장 중요한 발견

### ① 프로젝트 설명서를 인덱싱에 넣자 검색이 크게 개선됨

```
코드 청크:  @router.post("/pay")
            def pay(req): ...
            ↑ "결제 처리 진입점"이라는 말이 없음

설명서:     "결제 요청은 /pay 에서 시작하며 PaymentService 가 처리합니다"
            ↑ 질문과 같은 언어
```

**질문 표현과 청크 표현 사이의 간극을 설명서가 메꿔준 것입니다.**

### ② 짧은 질문·특정 함수 질문에 거의 답하지 못함

```
"validate_token 은?"     →  짧은 벡터 (정보량 적음)
1,200자 청크             →  긴 벡터
                            ↑ 코사인이 구조적으로 낮게 나옴
```

### 🔑 두 관측이 같은 곳을 가리킵니다

> **지금 인덱스에는 "코드가 무엇을 하는지 설명하는 말"이 없다.**

| 대응책 | 어느 관측 |
|---|---|
| **맥락 헤더** | ① 설명서 효과를 21,104개 청크 **전부에** 자동 적용 |
| **BM25** | ② 짧은 질문의 단어를 **길이 무관하게** 매칭 |

⚠ **둘 다 구현돼 있으나 기본은 꺼져 있습니다.** §4 참조.

### ③ `project_id` 혼선

```
질문:      "sqlalchemy 의 세션 관리는?"
project_id: "fest-api"        ← 백엔드가 고정값으로 보냄
   ↓
fest-api 컬렉션에서 검색  →  엉뚱한 답
```

**질문 내용으로 프로젝트를 자동 판별하지 않습니다.** `project_id` 만 봅니다.
의도된 설계이지만, **생성 규칙이 미정**이라 문제가 발생하고 있습니다.

→ 권장: workspace 폴더명. 상세는 `PROJECT_LIST_API_20260806.md` §4.

## 5. 설계 결정과 근거

⚠ **근거를 모르고 되돌리면 안 되는 것들입니다.**

### 임베딩 · 검색

| 결정 | 근거 |
|---|---|
| **BGE-M3 고정** | 다국어 — 한국어 질문 ↔ 영어 코드. 검색 실측의 전제 |
| **cosine 고정** | 임계값의 전제 |
| ~~저장소는 자유~~ | ⚠ **D9 으로 Chroma 확정.** 자유 항목 아님 |
| Chroma 선택 | 벡터 + **원문 + 메타**를 한 곳에 → 별도 DB 불필요 |
| **fallback 없음** | 가짜 임베딩이 조용히 인덱스를 오염시킨 사례 |
| **RRF 융합** | cosine(0~1)과 BM25(0~30+)는 척도가 달라 순위만 사용 |
| **임계값은 벡터 점수로** | D9 실측이 벡터 점수 분포에서 나온 값 |

### 인덱싱

| 결정 | 근거 |
|---|---|
| **git commit + fingerprint** | commit 만 보면 파라미터 변경을 놓침 |
| 경로 기반 청크 ID | 증분 인덱싱의 전제 |
| **증분: 임베딩 성공 후 삭제** | 임베딩 실패 시 데이터 소실 방지 (터널 끊김 관측됨) |
| `job_id` 미사용 | 동시 인덱싱 없음 → `project_id` 로 충분 |
| threading | Redis 6개 기능 중 필요한 건 2개 |
| `too_many_changes` 50% | 절반 이상 바뀌면 전체가 빠름 |

### 프롬프트 · 출처

| 결정 | 근거 |
|---|---|
| **프롬프트 조립을 rag_lab 이** | 학습 데이터와 **같은 코드**를 써야 형식이 안 갈라짐 |
| **LLM 호출은 백엔드가** | 스트리밍 중계 단계를 줄이기 위해 |
| 브리핑만 예외 | 스트리밍 불필요·1회성. model/url 을 주입받음 |
| **출처 2층** | 검색 단위는 파일이 아니라 청크 |
| **`n` 번호 유지** | 인용된 것만 추려도 재번호 금지 |
| history 0턴 권고 | 길면 근거를 밀어냄. 품질 저하 관찰됨 |
| 답변 길이 제한 폐기 | 스트리밍 전제에서 TTFT 와 무관. 실측 평균 98토큰 |

### 성능 실측

```
prefill    0.34 ms/token + 209ms 고정비   → 근거 2,400토큰에 1.0초
decode     약 53 tok/s                     → 300토큰 답변에 5.9초
콜드스타트  7.3초
임베딩     EC2 로컬 213ms / 터널 경유 약 800ms
검색       14ms (21,104 청크, Chroma)
문자/토큰  1.52 (한국어 혼합 마크다운)
num_ctx    8,192
```

**TTFT (최종 형태, 한 머신)**: 임베딩 213 + 검색 14 + prefill·첫토큰 600 ≈ **850ms** ✅
**TTFT (개발 중, 터널 경유)**: p50 1.6초 / p95 3.0초

⚠ 3초 목표는 **최종 형태 기준**입니다. 개발 중 지연은 제품 성능과 무관합니다.

### 🟡 6. 상태 영속성 — **성격이 바뀌었습니다 (2026-08-12)**

`data/state.json` 은 1단계 구현이고 SQLite 이관이 2단계 계획이었습니다.
**그런데 이건 저장 형식 문제가 아니라 "정본이 하나뿐"인 문제였습니다.**

관측된 사고:

```
Chroma 컬렉션 7개 / 임베딩 51,955  vs  state.json 이 아는 것 4개
→ 고아 3개를 몇 주간 아무도 몰랐음

그중 하나(fest-api, 40파일 · 전체의 1.5%)가 폴더명과 같은 이름을 차지
→ 그 이름으로 조회하는 모든 질문이 "근거 없음"으로 떨어짐
```

**대응은 SQLite 이관이 아니라 컬렉션 이름을 상태의 정본으로 만드는 것이었습니다.**

```
building-<pid>   인덱싱 중이거나 중단됨.  조회 대상 아님
<pid>-prev       교체 도중. 직전 인덱스의 백업
<pid>            완성된 인덱스.  이것만 조회됨
```

`state.json` 이 통째로 날아가도 Chroma 이름만 보고 복구할 수 있습니다.
상세는 `AGENTS.md` §2-6.

⚠ **SQLite 이관은 여전히 열려 있지만 우선순위가 내려갔습니다.** 형식보다 이중화가 문제였습니다.

| 반쪽 인덱스가 정상인 척 검색됨 | `Store.projects()` 가 미완성 제외 |

| `bm25_weight` | 0.4 | 🔴 임의값 (현재 RRF 라 미사용) |
| 청킹 전략 (줄 윈도우) | — | 🔴 **검증 안 됨** |

### 청크 크기 메모

**BGE-M3 는 8,192 토큰까지 받습니다.** 1,200자는 한참 여유입니다.
즉 **모델 제약 때문이 아니라 검색 품질 때문에** 자릅니다.

```
너무 크면  →  한 조각에 여러 주제 → 점수가 흐려짐
너무 작으면 →  함수가 중간에 잘림 → LLM 이 맥락 없이 설명
```

**최적값은 평가셋 없이 정할 수 없습니다.**

## 11. 용어

| 용어 | 뜻 |
|---|---|
| **청킹** | 파일을 조각으로 자르는 것 |
| **임베딩** | 텍스트를 1024개 숫자로. **검색용이지 LLM 입력이 아님** |
| **cosine similarity** | 두 벡터가 얼마나 비슷한가. 1.0=같음 |
| **임계값** | 이 점수 미만이면 "근거 없음" |
| **top_k** | 검색 결과 개수. **청크 개수이지 파일 개수가 아님** |
| **fingerprint** | 인덱스를 만든 파라미터 조합. 바뀌면 재인덱싱 |
| `[N]` | 답변 안의 인용 마커. `references` 의 `n` 과 대응 |
| **RRF** | 두 검색 결과를 순위 기반으로 합치는 방법 |
| **MMR** | 점수와 다양성을 함께 고려해 고르는 방법 |

### 🔑 자주 오해되는 것

> **LLM 은 벡터를 보지 않습니다. 원문을 봅니다.**

임베딩은 "어느 조각을 고를지" 정하는 데만 쓰이고,
고른 뒤에는 **원문 텍스트를 그대로** 프롬프트에 넣습니다.
