# 1. 불변 원칙 (결정이 아니라 전제)

## 프로젝트 정의

> 기업의 코드·문서·설계 지식을 통합 인덱싱(RAG)하고, fine-tuned LLM 이 이를 근거로 답하는
> **AI 코드 어시스턴트** — 신입 개발자 온보딩 지원.

## 핵심 원칙

- **지식은 검색(RAG)으로 공급, fine-tuning 은 "근거를 받아 인용해 설명하는 능력"을 학습**
- 모든 답변에 **출처 표시**
- **코드 비유출**: 사내 코드·문서가 외부 상용 API 로 나가지 않는다. LLM·임베딩 모두 자체 서버에서 구동한다.
  - ⚠ **네트워크 차단(air-gap)이 아니라 데이터 경계가 원칙입니다.** EC2 는 "사내 GPU 서버" 역할이며 데모·테스트 환경입니다.
  - ⚠ 2026-08-10 정정: 완전 폐쇄망 조건에서는 프로젝트 성립이 어렵다는 판단으로 인터넷 접속은 허용하는 방향으로 전환됨. 기존 "오프라인 구동" 표현을 "코드 비유출"로 교체.
- fine-tuned 모델은 공지 요건상 **1급 산출물로 유지**
- **표기 규칙**: "학습"은 공개 데이터 fine-tuning 에만. 기업/데모 레포 처리는 "인덱싱·분석"

## 차별점 3가지

1. 범용 도구(Copilot 등)가 모르는 "우리 회사" 코드·문서를 안다
2. 코드가 외부로 나가지 않는 온프레미스 구동
3. 모든 답변에 출처 표시

## D18 — 프롬프트 조립 = md 소유 ✅

- **시점** 7/31

> `Context` 가 설계의 핵심입니다. 형식 명세의 `contexts[]` 와 같은 스키마라서:
> ```
> Context ──┬──→ prompt_render()  →  추론 프롬프트

5. 임베딩 모델 또는 거리함수 변경
6. **판정에 쓰는 점수가 벡터 점수가 아닌 것으로 바뀜** (융합 점수 · 정규화 점수 · 리랭커 점수)
   ⚠ 1~5 는 "분포가 이동하는" 트리거인데, 6 은 **"분포 자체가 다른 것으로 바뀌는"** 경우라 성질이 다르고 영향이 더 큽니다.
7. **인덱스의 `context_header` 설정이 임계값 관찰 시점과 다름** *(2026-08-13 추가)*
   ⚠ 맥락 헤더는 모든 청크에 공통 어휘를 넣으므로 점수 분포가 이동할 수 있습니다. **방향·크기 미측정.**

### ⚠ 서술 규칙

```
금지:  "0.54 로 답할 수 있는 질문과 없는 질문이 분리됩니다"
사용:  "겹치는 분포에서 balanced accuracy 를 근사 최대화하는 잠정 선택값"
```

## 검색 — 신규 `[승인 대기]`

### `[제안 R1]` — 융합은 RRF, 점수 합산 아님 ✅

- **시점** 2026-08-06 관측 / 2026-08-12 흡수
- **결정** BM25 와 벡터 검색의 융합은 **RRF(Reciprocal Rank Fusion)** 로 한다. 두 점수를 가중 합산하지 않는다.
- **이유** cosine 은 유계(0~1)이고 BM25 는 **상한이 없다.** 척도가 다른 두 값을 더하면 가중치가 의미를 잃는다. **순위만 사용하면 척도 문제가 사라진다.**
- **부작용** `bm25_weight = 0.4` 는 RRF 채택으로 **현재 미사용**입니다.

⚠ **`D-R1` 과 커플링** — 아래 `[제안 R2]` 와 반드시 함께 읽어야 합니다.

### `[제안 R2]` — 근거 없음 판정은 **벡터 점수**로만 ✅

- **시점** 2026-08-06 / 2026-08-12 흡수
- **결정** 융합은 **순서만** 바꾼다. "근거가 있는가" 판정은 **벡터 점수**로 한다.
- **이유** `D-R1` 의 임계값 후보 평가가 **벡터 점수 분포**에서 이뤄졌습니다. 융합 점수로 판정을 옮기면 그 관찰이 통째로 무효가 됩니다.
- **변경 불가 조건** `D-R1` 이 재보정되기 전까지.
- **파생** (2026-08-13) 평가 하네스의 임계값 표도 **융합 전** 벡터 top-1 점수로 계산합니다. `--bm25 on/off` 에 영향받지 않는 것이 정상이며, 달라지면 버그입니다.

### `[제안 I6]` — 전체 인덱싱은 원자적으로 교체한다 ✅

> **2026-08-12 구현 완료.** 코드가 정본입니다 — `AGENTS.md` §2-6

```
금지:  store.reset(project_id)  →  임베딩  →  저장          (선삭제)
사용:  begin_build()            →  임베딩  →  promote()      (원자적 교체)

컬렉션 이름이 곧 상태:
    building-<pid>   인덱싱 중이거나 중단됨.  조회 대상 아님
    <pid>-prev       교체 도중. 직전 인덱스의 백업
    <pid>            완성된 인덱스.  이것만 조회됨
```

**이유 — 실제 사고에서 나왔습니다.**

```
선삭제로 기존 인덱스가 사라진 상태에서
state.json 쓰기 한 번이 실패(WinError 5) → 예외 → 인덱싱 전체 중단
→ 반쪽 인덱스가 남고, 그게 정상인 척 검색됨
```

관측 사례 2건 — 하나는 **결손 인덱스가 검색됐고**, 다른 하나는 **소스코드 0인 중단본이 폴더명과 같은 이름을 차지**해 그 이름으로 조회한 모든 질문이 "근거 없음"으로 떨어졌습니다.

**🔑 핵심 설계 원리**

> **`state.json` 이 통째로 날아가도 컬렉션 이름만으로 판정할 수 있어야 한다.**

**파생 규칙 4가지**

| | 규칙 | 이유 |
|---|---|---|
| 1 | **`promote()` 는 3단계** (prev 보존 → 승격 → prev 삭제) | 2단계로 줄이면 그 사이에 죽었을 때 인덱스가 사라집니다 |
| 2 | **`Store.projects()` 는 미완성을 제외** | 반쪽이 정상인 척 노출되던 것이 사고의 직접 원인 |
| 3 | **실패한 `building-*` 을 자동 삭제하지 않는다** | 남은 것이 중단의 증거입니다. 자동 삭제하면 원인을 못 찾습니다 |
| 4 | **서버 기동 시 경고만, 삭제는 명시적으로** | `cli.py` 가 별도 프로세스에서 인덱싱 중일 수 있습니다 |

**제약**

- Chroma 이름 규칙상 ASCII 영숫자로 시작해야 해서 `__building__` 같은 접두어는 **불가**
- 이름 상한 63자 → `project_id` 최대 **54자** (`store.MAX_PROJECT_ID`)
- 교체 중 **디스크가 일시적으로 2배**

⚠ **`status` 메타데이터는 상태의 정본이 아닙니다.** 이름만이 정본입니다. 실제로 `status: building` 이 남은 컬렉션이 정상 조회되고 있으며, 이 설계 덕분에 문제가 되지 않았습니다.

### `[제안 I7]` — 상태 기록 실패가 인덱싱을 죽이지 않는다 ✅

- **결정** `_save_all()` 재시도 5회(지수 백오프). 그래도 실패하면 **경고만 남기고 진행**

- ⚠ **트레이드오프**: 진행률 갱신이 성겨집니다. 프론트 진행바가 최대 2초 지연됩니다

**🔑 I6 과 I7 은 함께여야 의미가 있습니다.**

```
I6 (교체)    실패해도 안전하게 만든다

```

**하나만 고쳤으면 사고는 계속 났습니다.**

## 측정 — 신규 `[승인 대기]` *(2026-08-13)*

### `[제안 M1]` — 측정 기록의 조건은 **인덱스 지문**을 쓴다 ✅

- **시점** 2026-08-13
- **관측** `save_run()` 이 `CFG.fingerprint()` — **측정 프로세스의 환경변수** — 를 조건으로 적었습니다. 그건 "그 인덱스를 만들 때 실제로 쓴 값"이 아닙니다.

```
환경변수를 켜고 eval 을 돌림  →  기록에는 "켜고 쟀다"
그런데 조회한 인덱스는 꺼진 채로 만들어진 것
→ "맥락 헤더 켜고 쟀더니 이 값" 이라는 잘못된 문장이 성립
```

- **결정** 측정 기록의 조건은 `Store.index_fingerprint()` — **인덱스 자신이 들고 있는 지문** — 을 정본으로 한다. CFG 와 어긋나면 실행 시 경고한다. 지문이 없는 구 인덱스는 CFG 로 추정하되 **추정임을 `fp_source` 로 남긴다.**
- **파생** `make_measurements.py` 가 출처 불명 run 을 자동 격리합니다.
- ⚠ **기존 baseline 은 이 사고의 피해자입니다.** 수치 자체는 살아 있으나 조건을 특정할 수 없어 재측정 대상입니다.

### `[제안 M2]` — `eval_bm25` 와 `use_bm25` 는 다른 것이다 ✅

```
use_bm25   (인덱스 지문)  이 인덱스를 만들 때 역색인도 함께 만들었는가
eval_bm25  (측정 조건)    이번 run 에서 융합을 켜고 쟀는가  ← 검색 시점 스위치
```

- **이유** 두 개를 한 키로 기록하면 "역색인이 있다"와 "융합을 켜고 쟀다"가 구별되지 않습니다. 실제로 구별되지 않아서, BM25 융합 코드가 없던 시절의 run 에 `use_bm25: true` 가 기록됐습니다.
- **파생** **BM25 융합은 후처리가 아니라 검색 단계입니다.** 순위를 바꾸므로 Hit@k 에 직접 영향합니다. 평가에서 빼면 하이브리드 효과를 잴 수 없습니다.

### `[제안 I8]` — 경로 패턴 제외를 지문에 넣는다 ✅ *(2026-08-13)*

- **결정** `VSS_EXCLUDE_GLOBS` 로 경로 패턴 제외를 받고, `fingerprint()` 에 포함한다.
- **이유** `SKIP_DIRS` 는 **디렉터리 이름**만 봅니다. `docs/ko` 같은 하위 경로를 지정할 수 없습니다.
  실측에서 데모 레포의 74%가 12개 언어 번역본이었고, BGE-M3 가 다국어라 한국어 질문이

⚠ **인덱싱 전용입니다.** 질의 동작에는 영향이 없습니다 (`[제안 I9]` 참조).

### `[제안 I9]` — 지문 키를 **질의 영향 / 인덱싱 전용**으로 나눈다 ✅ *(2026-08-13)*

- ⚠ 인덱싱 전용 키가 어긋나도 `is_stale()` 은 True 가 됩니다 — 증분 갱신이
  전체 재인덱싱을 부르는 것은 여전히 실제 피해입니다.

### `[제안 R3]` — `top_score` 는 pool 안의 **최대 벡터 점수**다 ✅ *(2026-08-13)*

- **관측** `searcher` 가 융합 후 `hits[0]["score"]` 를 `top_score` 로 냈습니다.
  RRF 는 순서를 바꾸므로 `hits[0]` 이 최고점이 아닙니다. 실제로
  **`top < 임계값` 인데 `has_evidence: True`** 인 모순된 출력이 나왔습니다.
- **결정** `top_score = max(pool 안의 벡터 점수)`.
  판정이 `any(score >= th)` 이므로 이래야 **`top_score >= threshold ⟺ has_evidence`** 가 성립합니다.
- **추가** 융합 후 1위의 벡터 점수는 `ranked1_score` 로 따로 냅니다 (진단용).
- **파생** `cli.py search` 는 융합이 켜져 있으면 **"순서는 RRF 순위이지 점수순이 아니다"** 를 명시합니다.

⚠ 이 불변식을 깨는 변경은 하지 마세요. 표시와 판정이 어긋나면 **버그가 아닌 것을 버그로,
버그를 정상으로** 읽게 됩니다.

### `[제안 M3]` — 측정 문서는 기계 생성한다 ✅

# 11. 2026-08-14 구현 결과 — 질의 정본 복구와 프론트 파일 증분

> 기존 snapshot/Qdrant 설계를 폐기한 것이 아니라, 현재 질의 경로와 향후 snapshot 수신 경로의
> 책임을 분리한 결과입니다. 장시간 end-to-end 검증은 아직 완료하지 않았습니다.

### `[제안 I12]` — `/v1/chat`과 `/v1/search`의 검색 정본은 rag_lab이다 ✅

- **결정** FastAPI의 공개 `/v1/chat`은 rag_lab `/prompt`가 만든 `messages`를 그대로 생성 모델에
  전달하고, 생성 뒤 `/finalize`로 인용 출처를 확정한다.
- **결정** FastAPI `/v1/search`도 rag_lab `/search`를 사용한다.
- **NO_EVIDENCE** `has_evidence=false`이면 생성 모델을 호출하지 않고 답변은 `NO_EVIDENCE`,
  출처는 빈 배열로 반환한다.
- **이유** SQLAlchemy 코드 질문에서 rag_lab 직접 검색은 정답 파일을 찾았지만 FastAPI 경로는
  자체 Qdrant 검색을 사용해 일반론만 답하고 `[N]` 출처를 만들지 못했다.
- **경계** FastAPI의 PostgreSQL/Qdrant repository snapshot·generation 코드는 업로드·관리·향후
  snapshot 용도로 유지한다. 이를 현재 채팅 검색기로 사용하지 않는다.
- **프롬프트** 현행은 fine-tuning과 공유하는 rag_lab canonical prompt를 보존하기 위해 FastAPI의
  `history`와 frontend `context`를 messages에 추가하지 않는다. 향후 적용은 학습 계약과 함께 결정한다.

### `[제안 I13]` — 프론트 증분의 입력은 diff hunk가 아니라 변경 후 파일 전체 문자열이다 ✅

- **결정** 프론트는 `base_revision`, `target_revision`, 변경 파일의 프로젝트 상대경로와
  변경 후 전체 `content`, 삭제 경로, rename 정보를 보낸다.
- **결정** rag_lab은 로컬 checkout 없이 기존 전체 인덱싱과 같은 `chunk_text()`로 해당 문자열을
  청킹하고 기존 저장 fingerprint로 임베딩한다.
- **무결성** `content_sha256`은 선택값이다. 전달되면 검증하고, 생략되면 받은 문자열에서 계산한다.
- **동시성** `base_revision`은 현재 완성 인덱스 revision과 정확히 같아야 하며, 다르면 409로 거부한다.
  같은 `target_revision`이 이미 적용됐다면 idempotent 완료로 응답한다.
- **안전 순서** 새 청크의 모든 임베딩 성공 → 기존 경로 snapshot → Chroma 교체 → BM25 재구축.
  Chroma 또는 BM25 실패 시 직전 청크·벡터·역색인을 rollback한다.
- **전체 전환** 변경 영향이 설정값 50%를 넘으면 `too_many_changes`로 거부한다. 증분 실패나 거부를
  예고 없는 전체 인덱싱으로 자동 전환하지 않는다.
- **이유** 프론트가 파일 경로와 최종 content를 이미 안전하게 제공할 수 있으므로, diff hunk를
  재조립하거나 rag_lab 머신에서 동일 Git checkout을 강제할 필요가 없다.

### `[제안 I14]` — FastAPI는 파일 payload 증분의 얇은 프록시다 ✅

- **결정** Frontend → FastAPI → rag_lab `/index/update/files` 흐름을 사용한다.
- **FastAPI 책임** 인증, 요청 크기 제한, exact `project_id` 전달, upstream 202/400/409와 `reason`
  보존, `/index/status` 폴링 프록시.
- **비책임** FastAPI 안에 청킹·임베딩·Chroma·BM25·rollback 구현을 복제하지 않는다.
- **현재 상태** rag_lab endpoint와 실행 코드는 구현됐고 FastAPI 프록시는 다음 작업이다.
- **Open** 최대 파일 수·전체 byte, `base_revision` 정본 API, project ID 매핑, 증분 뒤 브리핑 재생성
  시점은 아직 합의되지 않았다.

### `[제안 I15]` — BM25 구축은 검증된 페이지 순회 후 staging 승격한다 ✅

- **결정** Chroma 전체 청크를 한 번의 `get()`으로 읽지 않고 `Store.iter_chunks()`로 제한된 크기의
  페이지를 순회한다.
- **완전성** 페이지 실패, 응답 배열 길이 불일치, 중복 ID, 순회 전후 건수 변경, 예상 문서 수 불일치는
  모두 실패다. 빈 목록 또는 부분 BM25로 성공 처리하지 않는다.
- **활성화** `lexical.build()`는 iterable을 끝까지 소비해 ID와 문서 수를 검증한 뒤 staging 파일에
  원자 저장한다. 전체 인덱싱·로컬 Git 증분·파일 payload 증분·재개 인덱싱 모두 검증된 staging만
  최종 BM25로 교체한다.
- **rollback** 증분 경로는 영향 파일의 Chroma snapshot과 직전 BM25를 보관하고, BM25 교체 이후
  fingerprint 저장까지 포함한 어느 단계에서든 실패하면 세 항목을 직전 상태로 복원한다.
- **이유** 큰 컬렉션의 무제한 Chroma `get()`이 SQLite 변수 제한으로 실패했는데, 기존 코드는 이를
  빈 목록으로 숨겼다. BM25가 전역 통계를 가지므로 부분 복구보다 완전한 입력 검증과 원자 교체가 안전하다.
- **검증** 대형 페이지 순회, 중간 페이지 실패, 중복 ID, 순회 중 건수 변경, 예상 건수 불일치,
  BM25 교체 뒤 증분 실패 rollback을 자동 테스트한다.
